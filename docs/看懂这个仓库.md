## 1. 这个项目是干什么的

老师批一份十几页的报告时，最累的不是打分，而是来回翻：评分表上有一条「问题定义值 4 分」，就得在报告里找出讲问题的那几段，再对照评分表决定给几分。下一条标准，又要重新翻一遍。

这个工具不替老师打分。它做三件事：

1. 把报告切成很多小段，每段记着第几页、哪一节。这些小段叫证据，编号像 `E-008`。
2. 每一条评分标准，只找出最相关的 5 段，交给 AI。AI 必须在每句判断后面标出用了哪一段。
3. 程序再检查 AI：编号是否真的存在、分数有没有超出满分、有没有一句夸奖却没标出处。不合格就打回去让 AI 改一次。还不合格，这条就不能直接接受。

最后屏幕上每一条都是「待决定」。老师点接受、改分或拒绝之后，才算批完。

一句话：**先找证据，再让 AI 带出处给建议，程序检查建议，人决定分数。**

## 2. 首页那张图，从左到右

首页图就是跑完「我们自己的 16 页 proposal」之后的界面。

### 最上面的五个数字

| 屏幕上的字 | 意思 |
|---|---|
| Criteria：6 | 这份评分表有 6 条标准 |
| Pages：16 | 报告有 16 页 |
| Evidence units：66 | 16 页被切成 66 个小段 |
| Pipeline latency：98 s | 整份跑完大约 98 秒 |
| Model：qwen2.5:7b | 用的是装在自己电脑上的 AI，不是网上的付费接口 |

标题下面那行小字的意思是：AI 给的分只是建议，最后由批卷的人决定。

### 黄条和蓝条

- **黄条**：有 2 条没通过检查，不能直接点接受。必须改分，或者拒绝这条建议。
- **蓝条**：另外 2 条，AI 第一次写错了。程序把错误发回去，AI 改了一次，第二次才通过。每条标准最多改一次。

### 左边

- **Review**：现在正在看的批改页。
- **Evaluation**：测试成绩页，全是指标，第一次不用看。
- **Run log**：这次 AI 调用的记录，可以事后重放。
- **Example**：已经选好了例子「Group 14 proposal v2」。也可以自己上传评分表和报告。
- **Gateway**：选中的是 local Ollama，也就是本地 AI。上面那个 Fixture 是假模型，只用来自动测试，不会真正阅读报告。
- **Evidence units per criterion (K)**：滑块在 5，表示每条标准只把最相关的 5 段给 AI。
- **Run review**：红色按钮，点了才开始批。

### 中间这条标准

展开的是第一条，R1，名称是 Problem, Background and Motivation（问题、背景和动机）。满分 1.5。

- 绿点 **sufficient**：证据够用来打分。这不是「写得好」，只是「找得到依据」。
- **suggested 1.5 / 1.5**：AI 建议给满分。
- 解释里的 `[E-008]`、`[E-004]` 是证据编号。**5/5 claims carry an evidence ID** 表示这 5 句都标了出处。
- **Draft feedback**：写给学生的一两句修改建议。
- **Top-band checklist**：满分描述里有哪些要点在报告里出现了。它不改分数，只是提醒。

### 右边才是真正的分数

四个选项：

| 选项 | 意思 |
|---|---|
| pending | 还没决定。现在就是这个状态 |
| accepted | 接受 AI 的建议分 |
| edited | 老师自己改分。AI 原来的建议仍会留下，方便以后对账 |
| rejected | 拒绝这条建议 |

分数框里的 1.50 是建议，可以改。在右边点选之前，这条不算批完，整份也不能导出。

## 5. 几个词

| 词 | 意思 |
|---|---|
| rubric | 评分表。每条标准有满分和每一档的描述 |
| evidence / E-008 | 报告里的一小段，带页码 |
| sufficient / partial / insufficient | 证据够 / 证据不完整 / 几乎没有证据。不是分数高低 |
| BM25、K=5 | 按关键词找出最相关的 5 段 |
| validator | 检查 AI 回答的那段程序，不是另一个 AI |
| pending | 老师还没决定 |
| baseline | 用来比较的对照做法。B2 是把整篇直接丢给 AI；B3 是规则相同，但把全部段落都给 AI |
